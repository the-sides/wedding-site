01The shape of the feature

Right now this site is effectively static. Notion posts are fetched at build time, and a Notion webhook hits /api/notion-webhook, which pings a Vercel deploy hook to rebuild the whole site. There is no per-request server work on any page a guest visits.

An RSVP form is the first thing that needs per-request work, because a submission has to be handled at request time. The decision, already made:

The plan

Stay static. Keep output: 'static', and mark only the RSVP and admin routes prerender = false. The form is a real <form> wired to an Astro Action that runs on submit. A client island can be layered on later for extra interactivity, but the form works without it.

This is the right call for this site, and it's worth being explicit about why the alternative is worse:

OptionConfigConsequence
Static + selective on-demand (chosen) output: 'static' plus export const prerender = false on only the RSVP and admin routes Guest-facing pages stay prerendered and CDN-fast. The Notion rebuild-on-webhook flow keeps working exactly as it does now. Only the RSVP endpoints run a function.
Fully server-rendered output: 'server' Every page becomes a function invocation. Your Notion pages would hit the Notion API on every request unless you add caching — and the deploy-hook rebuild loop becomes pointless. Rejected.

Astro 7 keeps this model unchanged from Astro 5: output: 'static' is the default, and prerender = false opts individual routes out of it. (The old output: 'hybrid' mode is long gone — static plus per-route opt-out is hybrid now.) You still need an adapter, because "some routes run on a server" requires one:

astro.config.mjs
import { defineConfig } from 'astro/config';
import vercel from '@astrojs/vercel';

export default defineConfig({
  // 'static' is the default — every page is prerendered unless it opts out
  adapter: vercel(),
});

Install it with bunx astro add vercel (this repo uses Bun), which installs the @astrojs/vercel version matching your Astro 7 install and edits the config for you. Don't pin the adapter by hand — Astro 7 ships on Vite 8, and a mismatched adapter is a confusing failure mode.

Watch for a conflict with the Astro port

The agent doing the Astro migration may have already set output: 'server' or added an adapter. Check astro.config.mjs before changing anything, and hold it to the decision above.

What Astro 7 changes for this feature

Most of what follows is version-stable. Four v7 changes do touch this work, and each is explained where it matters:

ChangeWhy it matters hereWhere
@astrojs/db removed entirely Astro's own database package no longer exists. Bringing your own Postgres — exactly what you're doing — is now the only path. It also means most "Astro + database" tutorials you'll find are dead. §5, §12
Rust compiler is now the default Unclosed tags are errors, and invalid HTML is no longer silently auto-corrected. A form is the most markup-dense thing you'll write, so this is where you'll meet it. §6
src/fetch.ts advanced routing (stable) Full control of the request pipeline, including running auth before Actions. The clean way to gate the admin page. §7
compressHTML defaults to 'jsx' Whitespace between inline elements is stripped by JSX rules rather than HTML rules. Occasionally visible in form label/input spacing. §11

Unrelated to RSVPs but relevant to the port in flight: v7 also swaps the default Markdown processor to Sätteri (remark/rehype plugins need migrating or @astrojs/markdown-remark reinstalled), and previously-experimental flags for the logger, queued rendering, the Rust compiler, advanced routing, and caching are now stable — delete them from astro.config.mjs if the port added any.

02Provisioning Neon

Two routes. They differ in who owns the environment variables.

Path A — via the Vercel Marketplace (recommended for this project)

Since the site already deploys to Vercel, installing Neon from the Vercel Marketplace means Vercel provisions the database and injects the connection variables into the project automatically — nothing to copy by hand, and it stays in sync.

# from the repo root
vercel integration add neon

# or: Vercel Dashboard → your project → Storage → Create → Neon

After it's linked, pull the variables down for local development:

vercel env pull .env

The integration sets these:

VariableWhat it isUse it?
DATABASE_URLPooled connection string (routed through PgBouncer)Yes — this is the one you want.
DATABASE_URL_UNPOOLEDDirect connection to the Postgres endpointOnly for migrations or long-lived sessions.
PGHOST, PGUSER, PGDATABASE, PGPASSWORD, PGHOST_UNPOOLEDThe raw pieces, if you need to assemble a custom stringNo.
POSTGRES_*Aliases kept for backwards compatibility with old Vercel Postgres templatesNo.

Pooled vs unpooled is the one connection concept worth internalising. Serverless functions come and go constantly; if each one opened a direct Postgres connection you'd exhaust the connection limit under any real traffic. The pooled string hands you a PgBouncer-managed connection instead. For a wedding RSVP form that's overkill in volume terms but it costs nothing and it's the correct default, so use DATABASE_URL everywhere except schema migrations.

Preview deployments get their own database branch

If you enable preview branching in the integration, each Vercel preview deploy gets branch-scoped connection variables injected at deploy time. Those values are deliberately not visible in the project's env var settings — they only exist for that deployment. Practical upshot: RSVPs submitted against a preview URL land in a throwaway branch, not production. That's the behaviour you want, but don't be confused when a test submission doesn't show up in the real table.

Path B — directly at neon.com

Create a project at console.neon.tech, copy the pooled connection string from the dashboard, and paste it into .env yourself. You then also have to add it manually to Vercel (vercel env add DATABASE_URL production). Choose this only if you want the database to outlive the Vercel project.

Either way the string looks like:

postgresql://USER:PASSWORD@ep-something-pooler.us-east-2.aws.neon.tech/neondb?sslmode=require&channel_binding=require

The -pooler in the hostname is how you tell at a glance that it's the pooled variant.

03Environment variables in Astro

Astro gives you two mechanisms. They are not equivalent, and for a database credential the difference matters.

The quick way: import.meta.env

const sql = neon(import.meta.env.DATABASE_URL);

Works, no config. But there's no type safety, no validation, and nothing stops a future you from importing that module into a client component and leaking the credential into the browser bundle.

The right way: astro:env

Astro's typed env schema lets you declare a variable as server-only and secret. Secrets declared this way are not included in the client bundle at all and are only reachable through the astro:env/server module — so an accidental client import becomes a build error instead of a leaked password.

astro.config.mjs
import { defineConfig, envField } from 'astro/config';
import vercel from '@astrojs/vercel';

export default defineConfig({
  adapter: vercel(),
  env: {
    schema: {
      DATABASE_URL: envField.string({
        context: 'server',
        access: 'secret',
      }),
    },
  },
});

Then, in server code only:

import { DATABASE_URL } from 'astro:env/server';
Build-time validation gotcha

Astro validates every secret in the schema whenever anything imports from astro:env/server — even variables you don't actually use in that file. If a CI build doesn't have DATABASE_URL set, the build fails. Either make sure the variable is present in every build environment (it will be, if you used the Vercel integration), or mark it optional: true and handle the undefined case.

Files to update

This repo already gitignores .env, and keeps a documented .env.example. Follow that convention — append to it in the same commented style as the Notion block:

.env.example
# Neon Postgres
# Pooled connection string. From the Vercel Neon integration
# (auto-injected in deployments) or the Neon dashboard.
# Run `vercel env pull .env` to populate locally.
DATABASE_URL=postgresql://user:pass@ep-xxx-pooler.region.aws.neon.tech/neondb?sslmode=require

04Installing the driver & the db.ts module

bun add @neondatabase/serverless

Neon works with any Postgres client (pg, postgres.js), but @neondatabase/serverless is the one to use here: it can issue queries over plain HTTP fetch instead of holding a TCP connection open. In a serverless function that runs for 40ms and dies, skipping the connection handshake is a meaningful latency win — and it works in any runtime that has fetch.

Two client shapes, and when each applies

neon() — HTTPPool / Client — WebSocket
Good forOne-shot queries; serverless request handlersMany queries in one session; interactive transactions
TransactionsNon-interactive only, via sql.transaction([...])Full BEGIN / COMMIT with logic in between

For your RSVP formThis one.Not needed.

An RSVP submission is "insert one row, maybe insert a few guest rows, return". That's a one-shot, and if you do need multiple statements atomically, sql.transaction() covers it without an interactive session.

src/lib/db.ts
import { neon } from '@neondatabase/serverless';
import { DATABASE_URL } from 'astro:env/server';

export const sql = neon(DATABASE_URL);

That's the whole client. There is no pool to configure and no connection to close — sql is a function that makes an HTTP request when you call it.

Your call: how much to put in this file

The pattern in src/lib/notion.ts is that the module owns the domain functions and callers never touch the raw client. Doing the same here — exporting createRsvp() / listRsvps() rather than bare sql — keeps SQL out of your route files and gives you one place to put types. Worth following, but it's a taste call.

Query syntax

The tagged template is the primary interface, and it parameterizes automatically:

const email = formData.get('email');
const rows = await sql`SELECT * FROM rsvps WHERE email = ${email}`;
//                                                  ↑ becomes $1, sent separately

The interpolated value is never spliced into the SQL text — it's sent as a bound parameter. This is what makes the template form injection-safe, and it's why you should reach for it by default.

Three escape hatches exist:

// 1. Manual parameterization, when you're building SQL programmatically
await sql.query('SELECT * FROM rsvps WHERE email = $1', [email]);

// 2. Composition — nested fragments keep their parameter numbering straight
const whereClause = sql`WHERE attending = ${true}`;
await sql`SELECT * FROM rsvps ${whereClause} ORDER BY created_at DESC`;

// 3. Raw interpolation — ONLY for values you control, never user input
await sql`SELECT * FROM ${sql.unsafe(tableName)}`;

Return shape

By default you get an array of plain row objects. If you want node-postgres-style metadata (rowCount, fields, command), construct the client with { fullResults: true }. For an RSVP form the default is fine.

05Designing and creating the schema

This is the most consequential decision in the whole feature

Everything below is a sketch to react to, not a spec to copy. The shape of your data follows from how you're inviting people, and only you know that.

Ignore anything you find about Astro DB

Astro 7 removed @astrojs/db entirely. A lot of the "add a database to Astro" material online is built on it and no longer applies — if a tutorial mentions astro:db, defineTable(), or db.insert(), it's for an older major. Bringing your own Postgres, the way this guide does, is now the supported path, and Astro's own migration advice points at Drizzle or plain drivers.

The modelling question: one table or two?

One flat table — one row per person who responds. Simple, easy to query, easy to export to a spreadsheet. Falls apart if you need "the Smith party has 4 seats" logic or a single invite code covering a household.

Two tables (parties + guests) — a parties row per invitation with an invite code and an allowed headcount, and a guests row per person. This is what you want if you're gating RSVPs behind a code, controlling plus-ones, or need "who hasn't responded yet".

Ask yourself: can a stranger who finds the URL submit an RSVP? If the answer must be no, you need the two-table model, because the invite code has to live somewhere and be checked server-side.

A starting schema

src/db/schema.sql
-- Adapt freely. Committing this file gives you a reviewable
-- record of the schema, which matters when there's no ORM.

create table if not exists parties (
  id            uuid primary key default gen_random_uuid(),
  invite_code   text unique not null,     -- what a guest types to unlock the form
  display_name  text not null,            -- "The Smith Family"
  max_guests    integer not null default 2,
  created_at    timestamptz not null default now()
);

create table if not exists rsvps (
  id            uuid primary key default gen_random_uuid(),
  party_id      uuid references parties(id) on delete cascade,
  name          text not null,
  email         text,
  attending     boolean not null,
  /* YOU WRITE THIS: meal choice? dietary notes? song request?
     plus-one name? which events (welcome dinner / ceremony / brunch)? */
  submitted_at  timestamptz not null default now(),
  updated_at    timestamptz not null default now()
);

create index if not exists rsvps_party_id_idx on rsvps (party_id);
Four things worth doing regardless of the shape you pick
  • timestamptz, never timestamp. Postgres's plain timestamp silently discards the offset; you will regret it the first time you look at submission times from a different timezone.
  • create table if not exists so re-running the file is harmless.
  • A uniqueness constraint on whatever identifies a person (e.g. unique (party_id, lower(name))). This is what lets you handle "guest submits twice" as an upsert instead of a duplicate.
  • Nullable rather than not null for optional fields — a guest half-filling the form should not 500.

Running it

No migration tooling is needed for a project this size. Pick one:

  • Neon SQL Editor — paste and run in the dashboard. Fastest for the first setup.
  • psql — psql "$DATABASE_URL_UNPOOLED" -f src/db/schema.sql. Use the unpooled string for DDL; PgBouncer's pooling mode doesn't play nicely with some session-level statements.
  • A one-off script — bun run src/db/migrate.ts reading the .sql file and executing it. Nice if you want it reproducible, overkill if you're editing the schema three times total.

Whichever you pick, apply schema changes to your Neon dev branch first (see §9), then to production.

06The write path — Astro Actions vs API routes

Astro gives you two ways to handle a POST. Given the plan — a real form that posts on submit, no island required — Actions are the right tool. The API route section is here for completeness and for anything a third party needs to call.

Option A — Astro Actions (the plan)

An Action is a server function with a Zod schema attached. Astro generates a type-safe client for it, validates input before your handler runs, and — the part that matters for a wedding site — supports plain HTML form submission, so the form works with JavaScript disabled or still loading. Some fraction of your guests will be on bad hotel wifi on a phone. That fraction gets a working form for free.

This is also what makes the "island later" plan cheap: the form action is the baseline behaviour, and an island is pure enhancement on top of a thing that already works.

src/actions/index.ts
import { defineAction, ActionError } from 'astro:actions';
import { z } from 'astro/zod';
import { sql } from '../lib/db';

export const server = {
  rsvp: defineAction({
    accept: 'form',              // parse FormData, not JSON
    input: z.object({
      /* YOU WRITE THIS — the schema *is* your validation.
         Notes on form-specific Zod behaviour:
           - text inputs      → z.string()
           - checkboxes       → z.coerce.boolean()
           - number inputs    → z.number()
           - repeated names   → z.array(...)
           - empty values arrive as null (except arrays/booleans) */
      name: z.string().min(1, 'Please tell us your name'),
      attending: z.coerce.boolean(),
    }),
    handler: async (input, context) => {
      /* YOU WRITE THIS — the insert.

         `input` is already validated and typed by the time you get here,
         so no manual checking is needed.

         Throw ActionError for expected failures — it becomes a typed
         error on the client rather than an unhandled 500: */
      // throw new ActionError({ code: 'NOT_FOUND', message: 'Invite code not recognised' });

      const [row] = await sql`
        INSERT INTO rsvps (name, attending)
        VALUES (${input.name}, ${input.attending})
        RETURNING id
      `;

      return { id: row.id };
    },
  }),
};

Consuming it from a plain Astro form

src/pages/rsvp.astro

import { actions } from 'astro:actions';

// Returns null on a fresh GET.

// Post/Redirect/Get — stops a browser refresh from resubmitting
if (result && !result.error) {
  return Astro.redirect('/rsvp/thanks');
}

<form method="POST" action={actions.rsvp}>
  {/* YOU WRITE THIS — your fields.

      `result.error` is populated on validation failure. Its
      `.fields` property maps field name → error messages, which is
      what you'd use to render inline errors next to each input. */}
</form>
export const prerender = false is not optional

A prerendered page has no server to POST to. Omit this line and the submission 404s or silently does nothing — and because the page still renders fine, it's an easy hour to lose. Put it on the RSVP page and on any admin page that queries the database.

Astro 7's Rust compiler will not forgive sloppy form markup

The Rust-based .astro compiler is the default in v7, and it changes two things you will hit while building a form: unclosed tags are now errors rather than being quietly accepted, and semantically invalid HTML is no longer auto-corrected. The Go compiler used to paper over both.

The usual offenders in a form: an unclosed <label> or <option>, a <div> nested inside a <p>, a stray </div> after refactoring a fieldset, or a nested <form>. These now fail the build instead of rendering something almost-right. That's a net win — the error is at build time rather than a mystery layout bug — but expect to meet it, and read the compiler error rather than assuming your Action is broken.

Later: adding a client island

This repo leans heavily on React (shadcn, Radix, Base UI), so at some point you may want richer interaction — live headcount validation, a nicer date/meal picker, optimistic UI. The action you wrote above is already callable from client code, no second endpoint needed:

import { actions } from 'astro:actions';

const { data, error } = await actions.rsvp({ name, attending });
if (error) { /* error.code, error.message, error.fields */ }
// or actions.rsvp.orThrow({ ... }) if you'd rather catch

The important part is how you add it. Keep the real <form method="POST" action={actions.rsvp}> as the markup, and let the island attach an onSubmit handler that calls the action and prevents the default. Then the no-JS path still submits normally and the island is pure enhancement. If you instead build a React form that only submits via onSubmit, you have quietly traded away the fallback — which is the one property that made Actions worth choosing in the first place.

Option B — a classic API route

If you'd rather own the HTTP layer, or the form is fully client-driven:

src/pages/api/rsvp.ts
import type { APIRoute } from 'astro';
import { sql } from '../../lib/db';

export const prerender = false;

export const POST: APIRoute = async ({ request }) => {
  const body = await request.json();

  /* YOU WRITE THIS: validate `body` yourself — there is no schema
     doing it for you here. Then insert, then shape the response. */

  return new Response(JSON.stringify({ ok: true }), {
    status: 201,
    headers: { 'Content-Type': 'application/json' },
  });
};

This is the shape the existing src/routes/api/notion-webhook.ts already has in TanStack terms, so it'll feel familiar. The cost relative to Actions is that validation, typing, and the no-JS path are all now your problem.

07The read path — an admin view of RSVPs

You'll want to see responses without opening the Neon console. In Astro, a page component's frontmatter runs on the server, so you can query directly there — no API layer needed:

src/pages/admin/rsvps.astro
---
import { sql } from '../../lib/db';

export const prerender = false;   // must query at request time

/* YOU WRITE THIS: gate access. Options, roughly in order of effort:
     - Vercel Deployment Protection / password protection on the route
     - a secret in the URL path (/admin/rsvps-9f2ac...) — weak but instant

   Do NOT ship this page ungated. Guest names, emails and dietary
   information are exactly the kind of thing you don't want indexed. */

  SELECT name, attending, submitted_at
  FROM rsvps
  ORDER BY submitted_at DESC
`;

Gating it with src/fetch.ts (Astro 7)

Astro 7 stabilised advanced routing: a src/fetch.ts file that exports a standard fetch handler and gives you full control over the request pipeline. It's the Cloudflare Workers / Deno shape, and it runs before Astro's own routing — which means before Actions, before middleware, before page frontmatter.

That ordering is the reason to use it here. A check in page frontmatter protects one page; a check in src/fetch.ts protects everything under /admin, including any endpoint you add later and forget to gate.

src/fetch.ts
import { astro, FetchState } from 'astro/fetch';

export default {
  fetch(request: Request) {
    const state = new FetchState(request);

    if (state.url.pathname.startsWith('/admin')) {
      /* YOU WRITE THIS: your check — a Basic auth header, a signed
         cookie, a shared secret. Return a 401/redirect to reject. */
    }

    // hand off to Astro's normal routing
    return astro(state);
  },
};

The same file is also how you'd proxy paths to an external backend, or run anything that must happen before an Action fires. You don't need it for the RSVP flow itself — the Action handles that fine — so treat it as the admin-gating tool and nothing more for now.

Also add /admin to public/robots.txt

The file already exists in this repo. Blocking crawlers isn't access control, but it costs one line and keeps guest data out of search results if the gate ever slips.

08Correctness & safety rules that actually bite

1. Never build SQL with string concatenation

// ✗ catastrophic — this is a SQL injection
await sql.query(`SELECT * FROM rsvps WHERE email = '${email}'`);

// ✓ parameterized
await sql`SELECT * FROM rsvps WHERE email = ${email}`;

The tagged template makes the safe thing the easy thing. The only way to get this wrong is to deliberately reach for sql.query() with a built string, or sql.unsafe() on user input.

2. Make resubmission idempotent

Guests will submit twice — double-click, back button, "wait, I need to add my husband". Decide what the second submission means. The usual answer is upsert:

INSERT INTO rsvps (party_id, name, attending)
VALUES (${partyId}, ${name}, ${attending})
ON CONFLICT (party_id, name)
DO UPDATE SET attending = EXCLUDED.attending, updated_at = now()

This requires the unique constraint from §5 to exist — ON CONFLICT needs an index to conflict on. If you'd rather keep a full history, insert every time and select the latest per person on read.

3. Multiple related inserts should be atomic

If one submission writes a party row plus several guest rows, a partial failure leaves you with half a household. The HTTP driver supports non-interactive transactions:

await sql.transaction([
  sql`INSERT INTO rsvps (...) VALUES (...)`,
  sql`INSERT INTO rsvps (...) VALUES (...)`,
]);

The limitation: you must know all the statements up front. If you need to read a value and branch on it mid-transaction, that's an interactive transaction — switch to Pool from the same package for that endpoint.

4. Assume the form will be found by bots

A public wedding site with a POST endpoint will get spam. Cheap defences, in order of value:

  • Invite code — the real fix. Nothing writes without a valid code.
  • Honeypot field — a visually hidden input that humans never fill; drop any submission where it's non-empty. Two lines, catches most naive bots.
  • Length caps in the Zod schema — z.string().max(200) on free-text fields stops someone pasting a novel into your database.
  • Vercel BotID — platform-level bot detection, if it becomes a real problem.

5. Don't leak database errors to guests

try {
  await sql`INSERT INTO ...`;
} catch (error) {
  console.error('RSVP insert failed:', error);   // full detail → Vercel logs
  throw new ActionError({
    code: 'INTERNAL_SERVER_ERROR',
    message: 'Something went wrong saving your RSVP. Please try again.',
  });
}

This matches how notion-webhook.ts already handles failures — log the real error, return something safe.

6. Small things

  • Create the client at module scope, not inside the handler. On Vercel's Fluid Compute, function instances are reused across requests, so module-level setup happens once instead of per-request.
  • 64 MB is the cap on HTTP query request/response size. Irrelevant for RSVPs; relevant if you ever store photos in Postgres (don't — use Vercel Blob).
  • Timeouts: fetchOptions: { signal } lets you abort a hanging query with an AbortController. Worth adding only if you see it in practice.

09Local development & Neon branching

Neon's branching is the feature that makes local development against a real database pleasant. A branch is a copy-on-write clone of your data — instant, effectively free, and fully isolated. You don't need Docker or a local Postgres.

# Neon dashboard → Branches → Create branch, or:
neonctl branches create --name dev

# Point local dev at the branch's pooled connection string
# in .env — production data stays untouched.

The workflow this enables:

  1. Develop and test schema changes against dev. Break things freely.
  2. When the schema is right, apply the same DDL to main.
  3. Before any risky change to production data, branch main first — that branch is your rollback.
Two env files, two databases

vercel env pull .env overwrites .env with production values. If you've pointed .env at your dev branch, that command will silently repoint you at production and your test RSVPs will land in the real table. Either re-edit DATABASE_URL after every pull, or pull into .env.production.local and keep .env hand-maintained.

10Deploy checklist

  • @astrojs/vercel adapter present in astro.config.mjs, installed via bunx astro add vercel so its version matches Astro 7 / Vite 8
  • No leftover experimental flags in astro.config.mjs — logger, queued rendering, Rust compiler, advanced routing and caching are all stable in v7 and the flags now error or warn
  • A clean production build passes — the Rust compiler rejects unclosed tags that dev may have tolerated in older majors
  • DATABASE_URL exists in the Vercel project for Production, Preview, and Development (automatic if you used the Marketplace integration — verify with vercel env ls)
  • DATABASE_URL declared in the env.schema block if you're using astro:env
  • export const prerender = false on the RSVP page, the admin page, and any API route
  • Schema applied to the production Neon branch, not just your dev branch
  • .env is gitignored (it already is) and .env.example documents the new variable
  • Admin route is gated, and /admin is in public/robots.txt
  • Submit a real RSVP on the preview URL, then confirm the row landed in the branch you expect
  • Check the function logs in the Vercel dashboard after that first submission — a silent failure looks identical to success from the browser

11Troubleshooting

SymptomLikely cause
Form submits but nothing happens; no server log Missing export const prerender = false. The page is static, so there's no handler to receive the POST.
DATABASE_URL is not defined at build time astro:env validates every declared secret when anything imports astro:env/server. The variable is missing from the build environment — add it, or mark it optional: true.
Works locally, fails on Vercel The variable exists in .env but was never added to the Vercel project, or was added only to Production and you're testing a Preview.
too many connections You're using DATABASE_URL_UNPOOLED in request handlers. Switch to the pooled string.
Client-side import error mentioning astro:env/server Correct behaviour — something in the browser bundle is importing db.ts. Find the import chain; a client component is pulling in server code.
Test RSVPs never appear in the table Preview deploys use a branch-scoped database. Check the Neon branch that corresponds to that deployment, not main.
ON CONFLICT raises "no unique or exclusion constraint matching" The unique index the upsert targets doesn't exist yet. Add it to the schema and re-apply.
Action returns a validation error you don't expect Empty form fields arrive as null, not "". Use .nullable() or .optional() on fields a guest can leave blank.
Build fails on form markup that "looks fine" Astro 7's Rust compiler. Unclosed tags are errors and invalid nesting is no longer auto-corrected. Read the compiler error — it points at the tag.
Spacing between labels, inputs or inline elements looks subtly wrong compressHTML now defaults to 'jsx', which strips whitespace between inline elements by JSX rules. Fix it in CSS (margin/gap) rather than relying on a literal space in the markup.
A tutorial's astro:db / defineTable() code won't resolve @astrojs/db was removed in Astro 7. That material is for an older major — use the Neon driver approach in this guide.
Requests behave oddly after adding an unrelated src/fetch.ts That filename is reserved in v7 as the advanced-routing entrypoint. Rename the file or set the fetchFile config option.

12Optional: adding Drizzle later

Drizzle is a TypeScript query builder that layers on top of the same Neon driver, giving you typed results and generated migrations. It's a good fit if the schema is going to keep moving — and with @astrojs/db gone in v7, it's now the closest thing Astro has to a blessed ORM story.

bun add drizzle-orm && bun add -D drizzle-kit
src/lib/db.ts (Drizzle variant)
import { neon } from '@neondatabase/serverless';
import { drizzle } from 'drizzle-orm/neon-http';
import { DATABASE_URL } from 'astro:env/server';

export const db = drizzle(neon(DATABASE_URL));

My honest read for this project: skip it. You have two tables and maybe three queries. Raw SQL in a tagged template is less code, less config, and nothing to learn. Reach for Drizzle if the schema grows past a handful of tables or you find yourself hand-writing migration ordering. Note that adding it later is cheap — the driver underneath is identical, so it's a swap of db.ts and your query call sites, not a rewrite.

13Your implementation checklist

The plumbing above is mechanical. These are the parts that need your judgement:

  • Decide the invitation model. Open to anyone with the URL, or gated by an invite code? This determines whether you need the parties table, and it's hard to retrofit once guests have started responding.
  • Decide the fields. Attending yes/no, headcount, meal choice, dietary restrictions, song requests, which events, a message to you. Every field is a chance for a guest to abandon the form — cut aggressively.
  • Write the schema in src/db/schema.sql and apply it to a dev branch.
  • Write the Zod input schema in the action. This is your validation layer; the handler should be able to trust its input completely.
  • Write the insert query, with an ON CONFLICT clause if you chose upsert semantics.
  • Build the form UI, deciding between a plain Astro form (works without JS) and a React island (better interactions).
  • Handle the three states: empty form, validation errors rendered inline, and success. The success state is the one people forget — a guest who doesn't get clear confirmation will submit again.
  • Build the admin view with a headcount and a CSV export. You will need the CSV for the caterer.
  • Gate the admin view before it ever ships to production.
  • Test the full path on a preview deploy before sending the link to anyone.
