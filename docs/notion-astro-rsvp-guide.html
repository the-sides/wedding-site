01Why this is a good idea here, and where it hurts

For a wedding RSVP list specifically, Notion is a better fit than it has any right to be. Three reasons, and they're not small:

  • You don't build an admin UI. With Postgres, "let me see who's responded" means writing a gated admin page, a table, a headcount, and a CSV export. With Notion, that's the database view you're already looking at. Filters, sorts, grouping by meal choice, a board view of who hasn't replied — all free, all instantly.
  • Vicki can use it without you. She can add a note to a guest's row, correct a spelling, mark someone as called. A Postgres table needs you in the loop for every edit.
  • Zero new infrastructure. @notionhq/client is already a dependency, NOTION_API_KEY is already in the environment, and src/lib/notion.ts already has working data-source resolution. You're adding one env var and one module.

The costs are real, though, and they're all consequences of one fact: Notion is a document store with a REST API, not a database.

  • ~3 requests per second. That's the connection rate limit. It's the single most important number in this guide — see §10.
  • No unique constraints, no upsert, no transactions. Deduplicating a double submission means query-then-write, which is racy by construction. §9.
  • Renaming a column in the UI breaks your writes. Property names are the API contract, and Notion lets anyone with edit access change them by double-clicking. There is no migration, no type checking, no warning.
  • Reads are slow and paginated. 100 rows per request. Fine at wedding scale, painful if you ever wanted live counts on a busy page.
The verdict for this project

Notion wins, and it isn't close — as long as you keep the invite list modest and don't put a live RSVP counter on the homepage. The admin UI you don't have to build is worth more than the constraints you give up, and the failure modes below are all manageable if you know about them in advance. That's what the rest of this document is for.

02The shape of the feature (+ what Astro 7 changes)

Identical to the Neon plan — the backend swap doesn't change the Astro architecture at all:

The plan

Stay static. Keep output: 'static', and mark only the RSVP route prerender = false. The form is a real <form> wired to an Astro Action that runs on submit. A client island can be layered on later for extra interactivity, but the form works without it.

Notably, with Notion you likely don't need an admin route at all, which removes a whole page, its auth gate, and its robots.txt entry from the Neon plan.

Astro 7 keeps the static-by-default model: output: 'static' is the default, prerender = false opts individual routes out, and an adapter is required for any route that runs on a server.

import { defineConfig } from 'astro/config';
import vercel from '@astrojs/vercel';

export default defineConfig({
  // 'static' is the default — every page is prerendered unless it opts out
  adapter: vercel(),
});

03Setting up the RSVP database in Notion

Build the schema in the Notion UI, not through the API. It takes two minutes, you can see what you're doing, and the API path for schema changes has sharp edges (§11).

Step 1 — create the database

Make a new database in your workspace. Give it a name you'll recognise in a URL bar. Keep it separate from the wedding-posts database — different content, different access needs, and see §4 for a sharper reason.

Step 2 — design the columns

This is the consequential decision

Notion property types are your schema. Changing them later is a UI click that can silently destroy data, so think it through once. Below is a sketch to react to, not a spec to copy.

ColumnNotion typeNotes
NameTitleMandatory — every Notion database has exactly one title property, and every page must have one. Use the guest's name so rows are readable at a glance.
AttendingSelect or CheckboxPrefer Select with Yes / No options over a checkbox. A checkbox can't distinguish "said no" from "hasn't answered".
EmailEmailNotion validates the format and makes it clickable.
Party sizeNumber
MealSelectOptions must exist or be creatable — see the warning below.
Dietary notesRich text2000 character cap. Fine, but validate shorter in your Zod schema.
Events attendingMulti-selectWelcome dinner / ceremony / brunch.
SubmittedCreated timeUse Notion's built-in Created time, not a date property you set yourself. It's automatic, always correct, and one less thing to write.
MessageRich textOptional note to you two.
Property names are your API contract

The keys in your properties payload must match the data source's property names exactly — including capitalisation and spaces. If anyone renames "Attending" to "Coming?" in the Notion UI, every RSVP write starts failing with a validation error, and nothing in your codebase will have warned you.

Two mitigations, in order of preference: (a) decide the names now and don't touch them, or (b) reuse the findPropertyName() helper that already exists in src/lib/notion.ts — it looks a property up by type with a list of preferred names and falls back to the first property of the right type. That's exactly the resilience this problem needs, and you already wrote it.

Step 3 — share the database with your integration

This is the step everyone forgets

Creating an integration is not the same as giving it access. Open the RSVP database → ⋯ menu → Connections → add your integration. Without it, every API call returns 404 object_not_found — not a permission error, which makes it maddening to debug. If your very first request 404s on an ID you copied correctly, this is why, essentially every time.

Your integration also needs insert content capability, since it's creating pages rather than just reading them. Check that in the integration's settings at notion.so/my-integrations.

Step 4 — get the data source ID

Since API version 2025-09-03, a Notion database is a container that holds one or more data sources, and you write pages to a data source, not to the database. Your .env.example already documents this distinction for the posts database — same idea here.

The reliable way to get it is the pattern already in your codebase:

const database = await notion.databases.retrieve({ database_id: DATABASE_ID });
if ('data_sources' in database && database.data_sources.length > 0) {
  return database.data_sources[0].id;
}

Run that once, note the ID, and put it in .env so you're not paying an extra API call on every submission.

04⚠ The deploy-hook trap

Read this before you create the database

This repo has src/routes/api/notion-webhook.ts, which receives Notion webhook events and triggers a full Vercel rebuild of the site. That's the right behaviour for wedding posts: you edit a post, the site rebuilds, the change goes live.

Now consider what happens if that webhook subscription covers your new RSVP database. Every single RSVP submission writes a page to Notion → Notion fires a webhook → your endpoint pings the deploy hook → the entire site rebuilds. Send out fifty invitations and you have fifty rebuilds queued, most of them redundant, some of them concurrent, all of them burning Vercel build minutes for no reason.

Worse, it's silent. RSVPs still save correctly. You'd only notice from the deployment list or the build-minutes bill.

What to do about it

Pick one, in order of robustness:

  1. Scope the webhook subscription to the posts database only. In the Notion integration's webhook settings, subscribe to the posts database specifically rather than workspace-wide events. Cleanest fix — the problem never occurs.
  2. Filter in the handler. The webhook payload identifies the source. Add an early return in notion-webhook.ts when the event's parent isn't the posts data source. This is worth doing regardless, as a belt-and-braces guard: 
    /* YOU WRITE THIS: near the top of the POST handler, before the
   deploy-hook fetch. Check the event's parent/data source against
   NOTION_DATA_SOURCE_ID and return early if it doesn't match. */
  3. Put the RSVP database in a different workspace. Heaviest option, only worth it if the other two are somehow impractical.

Do at least the second one. It's five lines and it makes the failure impossible rather than merely unlikely.

05Environment variables

You're reusing NOTION_API_KEY. The only genuinely new variable is the RSVP data source ID:

.env.example
# RSVP database
# Data Source ID for the RSVP database (NOT the posts one).
# In API v2025-09-03+, databases contain data sources and pages are
# created against a data source. Resolve it once via
# databases.retrieve() and paste the value here.
NOTION_RSVP_DATA_SOURCE_ID=xxx

Prefer astro:env over import.meta.env

The existing src/lib/notion.ts reads process.env.NOTION_API_KEY directly, which works. But this repo leans heavily on React islands (shadcn, Radix, Base UI), and an integration token in a client bundle would be a genuinely bad day — it grants write access to your workspace, not just the RSVP database.

Astro's typed env schema makes that mistake a build error instead of a leak. Secrets declared this way are excluded from the client bundle entirely and are only reachable through astro:env/server:

astro.config.mjs
import { defineConfig, envField } from 'astro/config';
import vercel from '@astrojs/vercel';

export default defineConfig({
  adapter: vercel(),
  env: {
    schema: {
      NOTION_API_KEY: envField.string({ context: 'server', access: 'secret' }),
      NOTION_RSVP_DATA_SOURCE_ID: envField.string({ context: 'server', access: 'secret' }),
    },
  },
});
import { NOTION_API_KEY } from 'astro:env/server';
Build-time validation gotcha

Astro validates every declared secret whenever anything imports from astro:env/server — even variables that file doesn't use. A build environment missing one of them fails the build. Make sure both are set everywhere you build, or mark them optional: true and handle undefined.

06The client module

No new dependency. @notionhq/client is already installed, and the existing module already constructs a client at module scope — the right place, since Vercel's Fluid Compute reuses function instances across requests.

src/lib/rsvp.ts
import { Client } from '@notionhq/client';
import { NOTION_API_KEY, NOTION_RSVP_DATA_SOURCE_ID } from 'astro:env/server';

const notion = new Client({ auth: NOTION_API_KEY });

export interface RsvpInput {
  name: string;
  attending: boolean;
  /* YOU WRITE THIS: the rest of your fields */
}

export async function createRsvp(input: RsvpInput) {
  return notion.pages.create({
    parent: { type: 'data_source_id', data_source_id: NOTION_RSVP_DATA_SOURCE_ID },
    properties: {
      /* YOU WRITE THIS — see §7 for the shape of each property type */
      Name: { title: [{ text: { content: input.name } }] },
      Attending: { select: { name: input.attending ? 'Yes' : 'No' } },
    },
  });
}
Your call: one client or two

You could import the existing client from src/lib/notion.ts instead of constructing a second one. Two clients with the same token is harmless — they're thin HTTP wrappers, not connection pools. Separate modules keep the RSVP write path independent of the posts read path, which I'd mildly prefer, but either is fine.

A note on API versioning

The SDK pins a Notion API version, and the version determines the shape of everything above — the data source model arrived in 2025-09-03, and Notion's current docs are already showing 2026-03-11. Your package.json has @notionhq/client ^5.8.0, and that caret means a bun update can move you to a newer minor with a newer default API version.

Nothing here is likely to break soon, but if RSVP writes start failing after a dependency bump with no code change, this is the first thing to check.

07Writing property values — the mapping table

This is the part that's fiddly the first time. Every property type has its own JSON shape, and the errors you get for a wrong shape are not especially helpful. Here is every type you're likely to need:

Notion typeJSON to send
Title{ title: [{ text: { content: "Jane Smith" } }] }
Rich text{ rich_text: [{ text: { content: "No shellfish" } }] }
Number{ number: 2 }
Select{ select: { name: "Yes" } }
Multi-select{ multi_select: [{ name: "Ceremony" }, { name: "Brunch" }] }
Checkbox{ checkbox: true }
Email{ email: "jane@example.com" }
Phone{ phone_number: "415-202-4776" }
Date{ date: { start: "2026-09-12" } }
Status{ status: { name: "Responded" } }
Created timeNothing — Notion sets it. Don't include it in the payload.

Three things that catch people:

  • Title and rich text are arrays of rich-text objects, not strings. This is the single most common mistake. { title: "Jane" } is a validation error; the nesting is title → array → text → content. It exists because Notion text carries formatting, links and mentions — you're just not using any of that.
  • Select options must exist, or be creatable. Sending { select: { name: "Vegan" } } when "Vegan" isn't an option on that property will either create the option or error, depending on the property's configuration. Don't let free-text user input flow into a select — map it to a known set of values in your action, and use Rich text for anything genuinely open-ended.
  • Omit rather than null for empty optional fields. If a guest leaves dietary notes blank, leave the key out of the payload entirely. Astro Actions hand you null for empty form fields, so build the properties object conditionally.

Size limits worth knowing

  • Rich text content: 2000 characters per value
  • Email: 200 characters. Phone: 200 characters. URLs: 2000
  • Multi-select: 100 options per request
  • Overall payload: 500 KB

None of these bind at wedding scale, but cap your free-text fields in the Zod schema anyway — it turns a Notion API error into a friendly validation message.

08The write path — the Astro Action

Same structure as the Neon plan: an Action with accept: 'form', so the form submits without JavaScript and an island is pure enhancement later.

src/actions/index.ts
import { defineAction, ActionError } from 'astro:actions';
import { z } from 'astro/zod';
import { createRsvp } from '../lib/rsvp';

export const server = {
  rsvp: defineAction({
    accept: 'form',
    input: z.object({
      /* YOU WRITE THIS — the schema *is* your validation.
         Form-specific Zod behaviour:
           - text inputs    → z.string()
           - checkboxes     → z.coerce.boolean()
           - number inputs  → z.number()
           - repeated names → z.array(...)
           - empty values arrive as null (except arrays/booleans)

         Cap free text so Notion's 2000-char limit can't be hit:
           dietary: z.string().max(500).nullable(), */
      name: z.string().min(1, 'Please tell us your name'),
      attending: z.coerce.boolean(),
    }),
    handler: async (input) => {
      try {
        const page = await createRsvp(input);
        return { id: page.id };
      } catch (error) {
        console.error('RSVP write to Notion failed:', error);
        throw new ActionError({
          code: 'INTERNAL_SERVER_ERROR',
          message: 'Something went wrong saving your RSVP. Please try again.',
        });
      }
    },
  }),
};

The log-real-error / return-safe-message split matches how notion-webhook.ts already handles failures. Keep it — a raw Notion validation error mentioning your property names is not something to show a guest.

src/pages/rsvp.astro

// Post/Redirect/Get — stops a refresh from resubmitting
if (result && !result.error) {

<form method="POST" action={actions.rsvp}>
  {/* YOU WRITE THIS — your fields.

      `result.error.fields` maps field name → error messages,
      which is what you'd use to render inline errors. */}
</form>
export const prerender = false is not optional

A prerendered page has no server to POST to. Omit this and the submission 404s or silently does nothing — and since the page still renders fine, it's an easy hour to lose.

Astro 7's Rust compiler will not forgive sloppy form markup

Unclosed tags are now errors, and semantically invalid HTML is no longer auto-corrected. The usual offenders in a form: an unclosed <label> or <option>, a <div> inside a <p>, a stray </div> after refactoring a fieldset, a nested <form>. These fail the build rather than rendering something almost-right. Read the compiler error before assuming your Action is broken.

Later: adding a client island

The action is already callable from client code — const { data, error } = await actions.rsvp({ ... }). Keep the real <form method="POST" action={actions.rsvp}> as the markup and have the island attach an onSubmit that calls the action and prevents the default. Then the no-JS path still works and the island is genuinely additive. A React form that only submits via onSubmit quietly throws away the fallback.

09Duplicates, and the upsert you can't have

Guests will submit twice — double-click, back button, "wait, I need to add my husband". In Postgres you'd write ON CONFLICT ... DO UPDATE and the database would guarantee correctness. Notion has no equivalent. No unique constraints, no atomic upsert, no transactions.

What you have instead is query-then-decide:

export async function findRsvpByName(name: string) {
  const response = await notion.dataSources.query({
    data_source_id: NOTION_RSVP_DATA_SOURCE_ID,
    filter: { property: 'Name', title: { equals: name } },
    page_size: 1,
  });
  return response.results[0] ?? null;
}

// then, in the action:
const existing = await findRsvpByName(input.name);
if (existing) {
  await notion.pages.update({ page_id: existing.id, properties: { /* ... */ } });
} else {
  await createRsvp(input);
}

Understand what this costs you:

  • It's racy. Two submissions arriving milliseconds apart can both see "no existing row" and both create one. There is no lock to take. You cannot fix this properly.
  • It doubles your API calls — a query plus a write for every submission, against a ~3/sec budget.
Your call — and I'd argue for the lazy option

Just let duplicates happen. Always create, never query. Then sort the Notion view by name and eyeball it, or use Notion's own duplicate-detection when you're finalising the list. You are going to read every row by hand before sending numbers to a caterer anyway.

This is a case where the Postgres instinct (enforce correctness at write time) is the wrong instinct for the medium. A human reviews this data before it matters. Spending API budget and race-condition risk to prevent a duplicate row that you'd spot in two seconds is a bad trade. Do the query-then-update dance only if you specifically want guests to be able to edit their response by resubmitting — which is a real feature, just be clear that's why you're paying for it.

10Rate limits & the RSVP thundering herd

The number to internalise: an average of three requests per second per connection, with some burst allowance above that. There's also a workspace-wide limit shared across all connections, scaled to your plan.

Exceeding it returns HTTP 429 with a rate_limited error code and a Retry-After header giving the seconds to wait. A 529 means Notion is overloaded and should be handled the same way.

Why this matters more than it looks

RSVP traffic is not smooth. It is the definition of bursty: you send fifty invitations on a Sunday evening, and a meaningful fraction of your guests open the link within the same hour — several within the same minute. Add a query-before-write dedup and each guest costs two requests.

You will probably be fine. Three per second is more than it sounds and this is a wedding, not a product launch. But "probably fine" plus "fails silently from the guest's perspective" is worth five lines of defence.

Handle 429 explicitly

import { APIResponseError } from '@notionhq/client';

/* YOU WRITE THIS — the shape:
   catch APIResponseError with status 429 or 529, read the
   Retry-After header, wait, and retry once. If it fails again,
   throw an ActionError with a message that tells the guest their
   RSVP did NOT save and to try again in a minute.

   The critical part is the guest-facing message. A silent failure
   here means someone believes they've RSVP'd and hasn't. That is
   the worst outcome this feature has. */
The design principle

Every failure mode in this feature should end with the guest knowing whether they're on the list. Ambiguity is worse than an error message — someone who sees "that didn't work, please try again" will try again, and someone who sees nothing will assume it worked.

Don't put a live counter on the site

It's tempting to show "132 guests attending" on the homepage. Resist it, or compute it at build time. A live count means a Notion query on every page view, which is both slow and a fast route to the rate limit. If you want it, the site already rebuilds on a webhook — fetch the count at build time and let it be a few hours stale.

11Changing the schema from code (the endpoint you linked)

PATCH /v1/data_sources/{data_source_id} updates a data source's schema and metadata — its title, icon, properties, parent database, and trash status. In SDK terms, notion.dataSources.update().

{
  "title": [{ "text": { "content": "Wedding RSVPs" } }],
  "icon": { "type": "emoji", "emoji": "💌" },
  "properties": { /* property configurations */ }
}

Within properties: add a property by including a new key with its type config, rename one by updating its name field, and delete one by setting it to null.

My recommendation: don't call this at runtime

Not because it doesn't work, but because there's no upside for you. Your schema changes maybe three times, always while you're sitting there designing the form, and the Notion UI does the same job with visual feedback and an undo button. Runtime schema mutation buys you nothing and adds a class of failure — a deploy that silently reshapes your live RSVP database — that you really don't want on a wedding site.

It's genuinely useful for a tool that provisions databases for other people. That isn't this.

If you do use it, the sharp edges

  • Some properties can't be updated via API at all — formula properties, synced content, and place properties are rejected.
  • Type conversions can destroy data. The docs call out people → file as a conversion that loses data. There's no dry-run and no undo.
  • Schema must stay under 50 KB. Oversized updates fail with a validation_error naming the largest property. Not a concern at your scale, but it's a real ceiling on select-option counts.
  • Relation properties require the related database to be shared with your connection too — the same Connections step from §3, applied to the other database.
  • Moving a data source to a different database converts existing views to linked views. Surprising if you weren't expecting it.

The one legitimately good use here: a startup assertion. Call dataSources.retrieve() (not update) when the module loads, check that the properties you write to exist with the types you expect, and throw a loud error if they don't. That turns "someone renamed a column and RSVPs have been failing for two days" into a deploy-time failure. Read-only, no risk, catches the schema-drift problem from §3.

12Notion vs Neon — the honest comparison

NotionNeon (Postgres)
New dependenciesNone — already installedOne driver package
New service to manageNoneA database, plus its env vars
Admin UIFree, and better than what you'd buildYou build it, and gate it
Vicki can edit responsesYes, directlyOnly through you
Write throughput~3 req/secEffectively unlimited here
Uniqueness / upsertNone — racy query-then-writeON CONFLICT DO UPDATE
TransactionsNoneYes
Schema safetyA UI rename breaks writes silentlyExplicit DDL, in version control
Query flexibilityFilter API, 100 rows/pageSQL
Export to catererBuilt-in CSV exportYou write it
CostIncluded in your Notion planFree tier is ample

The recommendation: Notion, for this project. The decisive factor isn't any single row above — it's that a wedding RSVP list is a human dataset. Fifty to two hundred rows, read by two people, edited by hand, cross-referenced against a seating chart, exported once to a caterer. The things Postgres is better at (integrity under concurrency, query flexibility, schema discipline) are things this dataset never really exercises. The thing Notion is better at — being a spreadsheet two humans can collaborate in — is the entire job.

Flip to Neon if any of these become true: you want guests to edit their RSVP after submitting and correctness actually matters; the guest list runs to many hundreds; or you find yourself wanting to join RSVP data against something else programmatically.

15Your implementation checklist

The plumbing above is mechanical. These are the parts that need your judgement:

  • Create the RSVP database in Notion and design its columns. Every field is a chance for a guest to abandon the form — cut aggressively.
  • Share it with the integration and confirm insert-content capability. Do this before writing any code, so your first API call isn't a mystery 404.
  • Scope or filter the webhook so RSVPs don't trigger rebuilds. Five lines, and it makes an expensive silent failure impossible.
  • Decide on duplicates: let them happen (recommended), or query-then-update if you want guests to be able to edit their response.
  • Write the Zod input schema. This is your validation layer — cap free text well under 2000 characters and map any select values to a known set.
  • Write the properties object, building it conditionally so blank optional fields are omitted rather than sent as null.
  • Handle 429 with a retry and a clear guest-facing failure message. The worst outcome this feature has is someone believing they've RSVP'd when they haven't.
  • Build the form UI and handle three states: empty, validation errors inline, and success. The success state is the one people forget — an unclear confirmation makes guests submit again.
  • Set up your Notion views: a filter for attending, a group by meal choice, a headcount rollup. This is the admin UI you're getting for free — spend ten minutes actually configuring it.
  • Test the full path on a preview deploy, including a deliberate failure, before sending the link to anyone.
